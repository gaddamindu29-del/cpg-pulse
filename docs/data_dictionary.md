# CPG Pulse - Data Dictionary

Two halves: the 9 **source datasets** (as generated/received, before any
transformation) and the **warehouse tables** (dbt-built, in `marts` schema)
that business users and the API actually query. Column lists below are
verified against real generated data (`data/sample/`) and a live warehouse
build, not just the original spec - a few fields carry generator- or
pipeline-specific notes where implementation details matter.

---

## Part 1 - Source Datasets

Generated by `scripts/generate_synthetic_data.py` (see `scripts/data_gen/`
for the full generation logic). Each is written in CSV, JSON, and Parquet.
Reference datasets are full-snapshot files; transactional datasets are
partitioned by `extract_date=YYYY-MM-DD/` (see `docs/architecture.md`
"Raw Layer").

### 1.1 Product Master (`product_master`) - reference

Internal ERP product master; the canonical product identifier space.

| Column | Type | Description |
|---|---|---|
| `product_id` | string | Canonical ID, format `P00001` |
| `upc` | string | 11-digit UPC. **Must stay a string** - see `docs/remaining_work.md` architectural decision #2 for the real bug this caused when it wasn't. |
| `brand` | string | e.g. `PeakRefresh` |
| `category` | string | One of 7 categories (Beverages, Snacks, Breakfast & Cereal, Personal Care, Household, Frozen Foods, Condiments & Sauces) |
| `subcategory` | string | e.g. `Sports Drinks` |
| `product_name` | string | Generated as `{brand} {subcategory} {flavor} {package_size}` |
| `flavor` | string | |
| `package_size` | string | e.g. `12-Pack Cans` |
| `case_quantity` | int | Units per case |
| `unit_cost` | decimal | Manufacturer's cost, category-range-based |
| `launch_date` | date | ~8% of products launch mid-dataset (new-item scenario) |
| `discontinued_date` | date, nullable | ~8% of products discontinue mid-dataset |

### 1.2 Store Master (`store_master`) - reference

| Column | Type | Description |
|---|---|---|
| `store_id` | string | Format `S-{retailer suffix}-0001` |
| `retailer_id` | string | FK to Retailers |
| `store_name` | string | |
| `city`, `state`, `region` | string | Region is one of 5 (Northeast/Southeast/Midwest/Southwest/West) |
| `store_format` | string | Retailer-specific (Supercenter, General Merchandise, Neighborhood Grocery, Online Fulfillment Center) |
| `latitude`, `longitude` | decimal | City-centroid + jitter, for map display only - not survey-accurate |
| `opening_date` | date | |
| `closing_date` | date, nullable | ~3% of stores close mid-dataset |

### 1.3 Retailer Product Mapping (`retailer_product_mapping`) - reference, SCD2 at the source

The critical cross-reference: retailer-specific SKU → canonical `product_id`.

| Column | Type | Description |
|---|---|---|
| `retailer_id` | string | |
| `retailer_product_id` | string | Retailer's own SKU, format `{suffix}-######` |
| `retailer_product_description` | string | Retailer's own (uppercase) item description |
| `product_id` | string | FK to Product Master |
| `match_method` | string | `EXACT_UPC` (70%), `FUZZY_NAME_MATCH` (15%), `MANUAL_REVIEW` (10%), `RETAILER_FEED_ID` (5%) |
| `match_confidence` | decimal | 0.97-1.0 for EXACT_UPC, 0.60-0.96 otherwise |
| `effective_start_date`, `effective_end_date` | date | **Already SCD2 at the source** - ~6% of mappings get remapped once mid-dataset (a retailer re-platforms its item feed). `effective_end_date IS NULL` = current. See `docs/remaining_work.md` architectural decision #2 for why this is *not* wrapped in a dbt snapshot. |

Retailer assortment (what fraction of the full catalog each retailer
carries) varies by banner: WMT 85%, TGT 70%, KRG 55%, AMZ 95%.

### 1.6 Calendar (`calendar`) - reference

| Column | Type | Description |
|---|---|---|

### 1.7 Promotions (`promotions`) - reference

| Column | Type | Description |
|---|---|---|
| `promotion_id` | string | |
| `retailer_id`, `product_id` | string | |
| `promotion_type` | string | Temporary Price Reduction, Feature Ad, Display Only, Feature + Display, Digital Coupon |
| `start_date`, `end_date` | date | 2-5 non-overlapping promo windows per (retailer, product) pair, 7/14/21/28 days |
| `regular_price`, `promotional_price` | decimal | |
| `discount_percentage` | decimal | 10/15/20/25/30% |
| `display_type` | string | End Cap, Aisle Display, Front of Store, Digital Banner, None |
| `marketing_spend` | decimal | Scaled by promo duration |

**Not exported** (internal to the generator only): a `true_lift_factor_internal`
column (1.4-2.8x ground-truth demand multiplier) drives the simulated sales
lift during promo windows - this is what `mart_promotion_effectiveness.sql`'s
*estimated* lift is being validated against (see `docs/metrics.md`).

### 1.8 Retail POS Sales (`retail_pos_sales`) - transactional

| Column | Type | Description |
|---|---|---|
| `retailer_id`, `store_id`, `retailer_product_id` | string | |
| `transaction_date` | date | |
| `units_sold` | int | |
| `gross_sales` | decimal | `units_sold * regular_price` |
| `discount_amount` | decimal | |
| `net_sales` | decimal | `gross_sales - discount_amount` |
| `regular_price`, `selling_price` | decimal | `selling_price < regular_price` during a promo |
| `sales_channel` | string | `IN_STORE`, `RETAILER_ONLINE`, `MARKETPLACE` (Amazon only) |
| *(post-2025-09-01 files only)* `promo_flag` | boolean | Compatible schema addition - see §1.9 schema evolution note |

**Injected data-quality issues** (`scripts/data_gen/quality_issues.py`):
~0.6% exact duplicates, ~1% nulls (in `discount_amount`/`sales_channel`),
~0.4% invalid `retailer_product_id` (references a SKU not in the mapping
table), ~2% late-arriving (extract_date 5-20 days after transaction_date
instead of the normal 1-2), ~0.15% price outliers (selling_price 10-100x
too high).

### 1.9 Retail Inventory (`retail_inventory`) - transactional

| Column | Type | Description |
|---|---|---|
| `retailer_id`, `store_id`, `retailer_product_id` | string | |
| `snapshot_date` | date | **Weekly cadence** in this dataset, not daily - see `docs/runbook.md` |
| `on_hand_units` | int | |
| `on_order_units` | int, nullable | Null-injected (`inventory_null_field_rate`) - standardization coalesces to 0 |
| `reserved_units` | int | **Schema evolution**: named `reserved_qty` in files with `snapshot_date < 2025-09-01`, renamed to `reserved_units` after. This is the concrete, deliberately-injected breaking-schema-change scenario referenced throughout `docs/architecture.md` section 11 and validated for real in `tests/integration/test_ingestion.py`. |
| `available_units` | int | `on_hand_units - reserved` |

### 1.10 Manufacturer Shipments (`manufacturer_shipments`) - transactional

| Column | Type | Description |
|---|---|---|
| `shipment_id` | string | |
| `retailer_id`, `distribution_center_id`, `product_id` | string | Note: `product_id` directly (canonical), not `retailer_product_id` - this is an internal ERP feed, not a retailer feed, so it never needed a retailer-specific identifier in the first place. |
| `shipment_date` | date | |
| `units_shipped` | int | |
| `shipment_status` | string | `DELIVERED` (85%), `IN_TRANSIT` (8%), `DELAYED` (5%), `CANCELLED` (2%) |
| `estimated_delivery_date` | date | |
| `actual_delivery_date` | date, nullable | Null for `IN_TRANSIT`/`CANCELLED`, plus an additional ~5% deliberately nulled even for `DELIVERED` (reporting-delay simulation) |

### 1.11 E-commerce Orders (`ecommerce_orders`) - transactional

CPG Pulse's own direct-to-consumer storefront - **not** a retailer channel.

| Column | Type | Description |
|---|---|---|
| `order_id` | string | |
| `order_date` | date | |
| `customer_id` | string | Synthetic UUID-like pool, no PII |
| `product_id` | string | Canonical ID directly (like shipments - no retailer mapping involved) |
| `units_ordered` | int | |
| `unit_price` | decimal | |
| `discount_amount`, `net_sales` | decimal | |
| `order_status` | string | DELIVERED (72%), SHIPPED (10%), PROCESSING (5%), CANCELLED (5%), RETURNED (8%) |
| `fulfillment_type` | string | STANDARD_SHIP, EXPEDITED_SHIP, SUBSCRIBE_AND_SAVE |
| `return_flag` | boolean | `True` iff `order_status = 'RETURNED'` |

## Part 2 - Warehouse Tables (`marts` schema)

Built entirely by dbt (`dbt run`) from the `landing` schema (see
`docs/source_to_target_mapping.md`). Verified column-for-column against a
live Postgres build - see `warehouse/postgres/warehouse_schema.sql` for the
complete DDL (also the source of truth over `warehouse/snowflake/*.sql`,
which was never executed against real Snowflake).

### 2.1 Dimensions

| Table | Grain | SCD Type | Key columns |
|---|---|---|---|
| `dim_date` | one row per calendar date | static | `date_sk` (int, YYYYMMDD) |
| `dim_retailer` | one row per retailer | Type 1 | `retailer_sk` |
| `dim_distribution_center` | one row per DC | Type 1 | `distribution_center_sk` |
| `dim_sales_channel` | one row per channel (seeded, static) | Type 1 | `channel_sk` |
| `dim_promotion` | one row per promotion | Type 1 | `promotion_sk` |
| `dim_product` | one row per product **per historical version** | **Type 2** (dbt snapshot) | `product_sk`; `effective_start_date`/`effective_end_date`/`is_current` track brand/category/subcategory/unit_cost/discontinued_date changes |
| `dim_store` | one row per store **per historical version** | **Type 2** (dbt snapshot) | `store_sk`; tracks region/store_format/closing_date changes |
| `dim_retailer_product_mapping` | one row per (retailer, retailer_product_id) **per historical version** | **Type 2**, natively from source-provided effective dates (not a dbt snapshot - see `docs/remaining_work.md` #2) | `retailer_product_mapping_sk` |

### 2.2 Facts

| Table | Grain | Materialization |
|---|---|---|
| `fact_retail_sales` | retailer × store × retailer_product × transaction_date × sales_channel | incremental (`delete+insert`) |
| `fact_inventory_snapshot` | retailer × store × retailer_product × snapshot_date | incremental |
| `fact_shipments` | one manufacturer shipment line | incremental |
| `fact_promotions` | retailer × product × promotion × activity_date (promo span exploded to one row per active day) | table (full rebuild) |
| `fact_ecommerce_orders` | order_id × product_id | incremental |
| `fact_data_quality_results` | one DQ check execution | table |

Full column lists: see `warehouse/postgres/warehouse_schema.sql` (every
column commented with its purpose) - not duplicated here to avoid the two
going out of sync; that file is the live-verified source of truth.

### 2.3 Analytics Marts (`marts/analytics`)

These are where the platform's actual business questions get answered - see
`docs/metrics.md` for formulas and `docs/architecture.md` for the underlying
logic design.

| Table | Grain | Answers |
|---|---|---|
| `mart_stockout_risk` | product × store × date | Which SKUs/stores are about to run out? |
| `mart_excess_inventory_risk` | product × store × date | Which SKUs/stores are overstocked? |
| `mart_shipment_pos_reconciliation` | retailer × product × week | Are shipments and consumer sell-through aligned? |
| `mart_promotion_effectiveness` | one row per promotion | Which promotions actually drove incremental sales? |
| `mart_omnichannel_performance` | channel_type × date | Physical vs. e-commerce performance |
| `mart_retailer_scorecard` | one row per retailer | Retailer-level KPI rollup |
| `mart_product_scorecard` | one row per current product | Product-level KPI rollup |
| `mart_data_quality_summary` | table_name × check_category | Aggregated DQ pass rates |

### 2.4 Pipeline Metadata (`pipeline_meta` schema, separate database)

Lives in the **metadata** database (`cpg_pulse_metadata`), not the warehouse
- see `docs/architecture.md` section 4 for why these are physically separate.
Full DDL: `warehouse/postgres/metadata_schema.sql`.

| Table | Purpose |
|---|---|
| `watermarks` | Last successfully-ingested extract_date per source, per environment |
| `pipeline_runs` | One row per ingestion/standardization/DQ/dbt task execution |
| `dq_results` | One row per data-quality check execution (source for `fact_data_quality_results`) |
| `schema_change_log` | Every detected schema drift event, compatible or breaking |
| `quarantine_log` | Index over rejected records (the rejected rows themselves live as files in the data lake's `quarantine/` layer) |
